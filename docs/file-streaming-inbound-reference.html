File Streaming Inbound Endpoint

Every parameter of org.wso2.carbon.inbound.streaming.VFSConsumer, its default, and four complete configurations. The inbound reads a file as a stream, so a multi-gigabyte CSV passes through a 1 GB heap without ever being held whole.

1 · Declaring parameters

Every parameter goes inside the <parameters> element of an inboundEndpoint, deployed to <MI_HOME>/repository/deployment/server/synapse-configs/default/inbound-endpoints/.

skeleton.xml

<?xml version="1.0" encoding="UTF-8"?>
<inboundEndpoint xmlns="http://ws.apache.org/ns/synapse"
                 name="myStreamInbound"
                 class="org.wso2.carbon.inbound.streaming.VFSConsumer"
                 sequence="mySeq" onError="myFaultSeq" suspend="false">
    <parameters xmlns="http://ws.apache.org/ns/synapse">
        <parameter name="scheduleType">Polling</parameter>
        <parameter name="interval">5000</parameter>
        <!-- ... the rest ... -->
    </parameters>
</inboundEndpoint>
MI 4.1.0 only

Use the class attribute with scheduleType, never protocol="polling" — MI 4.1.0 rejects it with No enum constant ... Protocols.polling. There is also no cronExpression support on this runtime; use interval.

2 · What one file does

  1. Poll the folder; skip anything not matching FileNamePattern.
  2. Take the .lock beside the file.
  3. Look for a checkpoint. Resumable → start at record N. Otherwise → start at record 1.
  4. Read one chunk or record.
  5. Inject it into the sequence.
  6. Append whatever the sequence left to the reply file.
  7. Every CheckpointInterval units, write the checkpoint.
  8. Repeat from step 4 until the file is exhausted.
  9. Clear the checkpoint, run FileCompleteSequence, move the file to MoveAfterProcess.

A graceful shutdown interrupts the loop at steps 4–8: the inbound finishes the record in flight, writes a checkpoint, releases the lock and leaves the file where it is. Neither completion sequence fires — the file is paused, not finished.

3 · Inbound plumbing

Synapse-level parameters, not specific to this inbound.

ParameterDefaultWhat it does
scheduleType REQ—Must be Polling. Pairs with the class attribute.
interval REQ—Milliseconds between polls of the source folder.
sequentialtrueWhether polls run one at a time. Streaming always delivers records sequentially within a file whatever this is set to; it only affects concurrency across polls.
coordinationtrueIn a cluster, only the coordinator polls. Leave it on, or several nodes will fight for the same file.

The sequence attribute names the sequence each chunk or record is injected into; onError names the fault sequence.

5 · Streaming core

Names below omit the transport.vfs. prefix.

ParameterDefaultWhat it does
Streaming REQfalseMust be true for CHUNK or RECORD mode. Left at the default, the inbound takes the whole-file path regardless of StreamingMode.
StreamingModeENTIRE_FILE
  • ENTIRE_FILE — one message for the file. No streaming, no checkpointing.
  • CHUNK — a JSON array of StreamingChunkSize records per message.
  • RECORD — one JSON object per message.
StreamingInputFormattextHow the bytes are parsed: text, csv, json, jsonl or xml.
StreamingChunkSize1Records per message in CHUNK mode. 1000–5000 is the usual range; larger means fewer mediations but a bigger live payload.
StreamingBufferSize8192Read-buffer bytes. 65536 measurably helps on multi-gigabyte files.
StreamingCharsetUTF-8Character set used to decode the file, and appended to the content type.
Easy to miss

transport.vfs.Streaming defaults to false. Setting StreamingMode alone does nothing — both are needed.

6 · CSV parsing

Names below omit the transport.vfs. prefix.

ParameterDefaultWhat it does
StreamingCsvHasHeadertrueTreat the first line as column names. The header is consumed, not delivered as a record.
StreamingCsvDelimiter,Field separator. Only the first character is used.
StreamingCsvQuote"Quote character.
StreamingAddHeadersToEachResultfalsefalse emits a row as an array ["1","Alice"]; true emits it as an object {"id":"1","name":"Alice"}. Almost always set this to true.
StreamingCsvDataTypesstringsJSON array declaring the type of named or positional columns. Alias: transport.vfs.csvDataTypes.

Column data types

CSV carries no types, so without this every field is emitted as a string and a sequence cannot do arithmetic on it. The mapping is declared once on the inbound:

<parameter name="transport.vfs.StreamingCsvDataTypes">[
  {"Column Name Or Index":"order_id",   "Is Column Name":"Yes", "Data Type":"Integer"},
  {"Column Name Or Index":"unit_price", "Is Column Name":"Yes", "Data Type":"Number"},
  {"Column Name Or Index":"2",          "Is Column Name":"No",  "Data Type":"Boolean"}
]</parameter>
KeyValuesMeaning
Column Name Or IndexstringA header name, or a zero-based column index as a string.
Is Column NameYes / NoYes reads the first key as a header name, No as an index.
Data TypeString · Integer
Number · Boolean		The JSON type the value is emitted as.

A value that will not convert is left as a string and the column is warned about once per file, never once per row — a bad column in a million-row file produces one log line, not a million. Nothing is dropped and nothing fails.

With the mapping above, the row 4,Dave,N/A,7 yields {"order_id":4,"name":"Dave","unit_price":"N/A","qty":"7"}: order_id typed, unit_price left alone because N/A is not a number, qty untouched because it was not declared.

7 · JSON, JSONL, XML, text

Names below omit the transport.vfs. prefix.

ParameterDefaultWhat it does
StreamingJsonPath$[*]Selects the repeating element in a json file. Applies only to StreamingInputFormat=json.

The other formats need no parameters of their own:

  • jsonl — one JSON value per line. Each line is a record; no path needed.
  • xml — repeating child elements become records.
  • text — one line is one record. The default format.

For a document shaped {"meta":{...},"orders":[...]}, the selector $.orders[*] makes each element of orders one record and ignores meta. The default $[*] suits a file that is a bare top-level array.

8 · Where output goes

Names below omit the transport.vfs. prefix.

ParameterDefaultWhat it does
StreamingOutputPropertyunsetName of a Synapse property to put the parsed JSON into. Unset, the parsed content becomes the message body instead.

Read it in a sequence with get-property('<name>'). The value is a JSON object in RECORD mode and a JSON array in CHUNK mode, as a string.

Why a property, not a variable

MI 4.1.0's Synapse has no message variables. The upstream parameter name transport.vfs.StreamingOutputVariable is still accepted as an alias so existing configurations keep working.

9 · Reply file

Names below omit the transport.vfs. prefix.

ParameterDefaultWhat it does
ReplyFileURIunsetDestination folder for the mediated output. Unset, nothing is written.
ReplyFileNameresponse.jsonl
response.xml		Output file name. The default depends on the payload: JSON lands in response.jsonl, anything else in response.xml.

The payload decides the format, not the input: JsonUtil.hasAJsonPayload() picks the JSON path, otherwise the message is serialised with the registered message formatter for its content type. Append is forced, not a choice — a streaming run writes one file per source file and adds to it on every loop.

Keep the payload on one line

A <payloadFactory> whose <format> spans several lines writes multi-line entries and breaks JSON Lines. Compact the format onto one line.

An empty body is skipped rather than written as a blank line, and a destination that cannot be opened fails softly: the source file has already been delivered to the sequence, so it is not failed over a reply-file problem.

10 · Error handling

Streaming separates a bad record from a bad file. A bad record never fails the file.

Names below omit the transport.vfs. prefix.

ParameterDefaultWhat it does
StreamingParseErrorActionMOVEMOVE collects records that would not parse; DROP discards them.
StreamingParseErrorFolderunsetWhere the collected parse failures are written.
StreamingMediationErrorActionMOVESame, for records the sequence threw on.
StreamingMediationErrorFolderunsetWhere the collected mediation failures are written.

Failed records are collected as JSON Lines: input.jsonl produces input.parse-failed.jsonl and input.mediation-failed.jsonl. Every file ends with a summary line giving the totals:

INFO {StreamInjectHandler} - Streaming completed for orders-1gb.csv:
  processed=8663312, parseFailed=0, mediationFailed=0 (resumed from record 7506000)

The whole-file failure parameters (ActionAfterFailure, MoveAfterFailure) still apply to a file that cannot be opened or read at all.

11 · Checkpointing

A long file that is interrupted resumes near where it stopped instead of re-reading from the start.

Names below omit the transport.vfs. prefix.

ParameterDefaultWhat it does
StreamingCheckpointEnabledtrueWhether a resume point is written at all.
StreamingCheckpointInterval1000Units between writes — chunks in CHUNK mode, records in RECORD mode. With ChunkSize=2000, an interval of 50 is a resume point every 100,000 rows.
StreamingReadRetries3Consecutive read failures without progress tolerated when the connection drops mid-file (SFTP Pipe closed, connection reset). Each time the file is opened again over a new connection, the bytes already read are skipped and reading carries on at exactly that byte: no record is repeated or lost, and the checkpoint is untouched. A stream that ends before the file's original size counts as a drop too. 0 turns it off: the first failure fails the file, as before.
StreamingReadRetryDelay5000Pause before a read retry in milliseconds, multiplied by the failure count (5 s, then 10 s, then 15 s with the default).

Only CHUNK and RECORD checkpoint. ENTIRE_FILE is a single message, so there is no position to record.

Where it lives

The MI registry — a file-based governance registry, no database:

gov:/fileStreamingCheckpoints/<inboundName>/<crc32 of the file URI>.json

One in-flight checkpoint per source file, plus a .bak holding the previous write and a .meta sidecar the registry keeps. The .bak exists so a crash during the write itself still leaves a usable resume point.

The source URI is never stored. The resource is named by a CRC32 of it and the body carries only a SHA-256, because an sftp:// or smb2:// URI carries credentials and in a cluster the registry is a shared mount.

What is stored

b9aca662.json

{"schemaVersion":1,"inboundName":"bigOrdersInbound",
 "fileUriHash":"9fc088a9528588977f0a0ddbb34d0ff4e38ca6b476b427b85d3eab5b6f103f65",
 "fileFingerprint":{"size":1073749726,"lastModified":1791264772944,"hashedBytes":65536,
                    "algorithm":"CRC32","hash":"5aa6208e"},
 "streamingMode":"CHUNK","inputFormat":"csv","configHash":"da5db5",
 "recordsConsumed":2812000,"chunksConsumed":1406,"processedRecords":2812000,
 "parseFailedRecords":0,"mediationFailedRecords":0,"updatedAt":1791264811852}

chunksConsumed is what keeps chunk numbers counting up after a restart instead of going back to 1. The counters keep the final totals absolute across a resume.

File identity is content, not timestamp

A checkpoint is only used when the file still matches the fingerprint recorded with it: byte count + CRC32 of the leading 64 KB + the hash budget and algorithm. The modification time is recorded and printed in diagnostics but is not compared.

Why mtime is excluded

Comparing it broke resume in a cluster. Two nodes reported the same local file's mtime as 1791263539594 and 1791263539000 — one instant, the second truncated to a whole second, because the precision depends on the file system and on how the FileObject was resolved. The second node judged the file changed and re-read all of it from record 1. The same comparison also rejected a file moved away and copied back with identical bytes.

The config hash is the other interlock, covering format, mode, chunk size, charset, CSV delimiter/quote/header, JSON path, output property and column data types. Change any of them and the old position is meaningless, so the file starts fresh rather than skipping the wrong records.

Why a resume did not happen

A refused resume costs a full re-read, so the reason is always logged.

Log lineLevelMeaning
No streaming checkpoint at <path>…INFONothing to resume from — the ordinary case for a new file.
Ignoring the streaming checkpoint… because <reason>WARNOne was found and refused. The reason names the differing fields, e.g. the file changed since the checkpoint was written (size 42->1073749726 …).
The primary streaming checkpoint… was unreadableWARNThe main resource was corrupt; the .bak was used.

If checkpointing cannot start at all — no registry, or the file cannot be fingerprinted — the file streams without resume support and a warning is logged. It is never a failure.

Sharing the registry across a cluster

For one node to resume what another started, both must read the same governance registry. Point the second node's GovRegRoot at the first node's registry in <MI_HOME>/repository/deployment/server/synapse-configs/default/registry.xml:

node2 · registry.xml

<registry xmlns="http://ws.apache.org/ns/synapse"
          provider="org.wso2.micro.integrator.registry.MicroIntegratorRegistry">
    <parameter name="cachableDuration">15000</parameter>
    <parameter name="GovRegRoot">file:///shared/node1/registry/governance</parameter>
</registry>
Do not symlink it

Symlinking registry/governance breaks reads: MicroIntegratorRegistry resolves the canonical path and checks it still sits under the configured root, and a symlink fails that test. Writes keep working, which hides the problem. Use GovRegRoot.

12 · Completion sequences

Two optional sequences fire once per file, after the last record, carrying the file's totals.

Names below omit the transport.vfs. prefix.

ParameterDefaultWhat it does
StreamingFileCompleteSequenceunsetInvoked after a file is fully consumed.

{"file":"orders-1gb.csv","uri":"file:///data/in/orders-1gb.csv","status":"COMPLETED",
 "processed":8663312,"parseFailed":0,"mediationFailed":0}
PropertyValue

13 · Locking

A .lock file beside the source stops two nodes consuming it at once.

Names below omit the transport.vfs. prefix.

ParameterDefaultWhat it does
Lockingenableenable or disable. Keep it on for any shared or clustered source.
AutoLockReleasefalseReclaim a .lock left behind by a hard kill. Without it, a killed server's lock blocks the file forever.
AutoLockReleaseIntervalnoneMilliseconds a lock must exceed in age before it may be reclaimed. Unset means reclaim at any age.
LockReleaseSameNodetruetrue reclaims only a lock written by this host — a live node's lock is never stolen. false allows reclaiming another node's.

A lock file holds random:hostname:hostip:timestamp. The age is the difference between the current lock's timestamp and the new one's; if it cannot be parsed, the lock is left alone rather than reclaimed on a guess.

After a kill -9

The symptom is Couldn't get the lock for processing the file: … on every subsequent poll. Set AutoLockRelease=true with an interval comfortably longer than a normal poll, or delete the stale .lock by hand.

14 · After processing

Names below omit the transport.vfs. prefix.

ParameterDefaultWhat it does
ActionAfterProcessDELETEMOVE or DELETE, on success.
MoveAfterProcessnoneDestination folder when the action is MOVE. Required in that case.
ActionAfterFailureDELETEMOVE or DELETE, on failure.
MoveAfterFailurenoneDestination folder for failed files.
ActionAfterErrorsinheritsAction for files that errored rather than failed outright.
MoveAfterErrorsinheritsDestination for those.
MoveAfterFailedMovenoneWhere to put a file whose move itself failed.

A file interrupted by a graceful shutdown is not moved to the failure folder. It stays in the input folder with its checkpoint and is resumed on the next poll.

A separate failed-record retry family exists (MaxRetryCount, FailedRecordNextRetryDuration, FailedRecordsFileName, FailedRecordsFileDestination, MoveFailedRecordTimestampFormat, MoveAfterFailedMove) and is inherited from the base VFS transport. In streaming mode the per-record error folders above are the ones that matter.

15 · Remote connections

transport.vfs.FileURI carries the protocol, the credentials and any VFS options as query parameters.

// local
/data/in
file:///data/in

// sftp, with VFS options
sftp://user:pass@host:22/incoming?vfs.passive=true

// ftp / ftps
ftp://user:pass@host/incoming?vfs.passive=true

// smb2
smb2://user:pass@host/share/incoming
ProtocolNeeds
fileNothing. Shipped with MI.
ftp / ftpsShipped with MI's commons-vfs.
sftpShipped with MI's commons-vfs.
smb2The smbj and asn-one bundles, present in MI 4.1.0. Requires commons-vfs 2.2.0-wso2v13.20 or later, which carries the sandbox smb2 provider.

SFTP tuning

Names below omit the transport.vfs. prefix. Each can also be given as a query parameter on the FileURI without the SFTP prefix, e.g. ?Timeout=45000.

ParameterDefaultWhat it does
SFTPTimeoutnoneSocket read timeout in milliseconds for the SFTP session.
SFTPConnectTimeout30000TCP connect timeout in milliseconds. Defaulted deliberately — jsch otherwise waits forever, and a connect that has not completed in 30s never will.
SFTPIdentitiesnonePrivate key file(s) for key-based authentication.
SFTPIdentityPassPhrasenonePassphrase for those keys.
SFTPUserDirIsRoottrueWhether a relative path is resolved against the login directory.
Why the poller can hang without this

jsch has no timeout by default. A server that accepts the TCP connection and then stops responding blocks the polling thread indefinitely — not only while reading a file, but on the metadata calls made before one is even opened, such as the exists() check in Utils.isFailRecord. One stalled host takes the inbound down until MI is restarted. Set SFTPTimeout on any SFTP source you do not control.

Choosing a value, and why there is no default

SFTPTimeout also bounds reads taken while a file is streaming, and those are paced by how fast your sequence mediates each record — not by the network. Set it comfortably above the slowest gap between two reads, not just above the round-trip time, or a healthy but slow transfer is cut off. There is no safe universal value, so there is no default.

Update level matters

SFTPConnectTimeout is honoured from commons-vfs 2.2.0-wso2v13.20 (MI 4.1.0 at a current update level), whose SftpClientFactory reads it and calls Session.connect(int). A server still on _18 has no such setter and calls Session.connect() with no argument; the inbound detects that, logs one line, and lets SFTPTimeout bound the connect as well. One binary works on both.

Passwords in a FileURI are masked in every log line the inbound writes, and never reach the checkpoint.

16 · Context properties

Position properties are stamped on every streamed message, whether the parsed output went to a property or to the body. They let a sequence tell which rows it is holding.

PropertySet inValue
STREAMING_RECORD_NUMBERRECORDAbsolute 1-based record number in the file.
STREAMING_CHUNK_NUMBERCHUNKAbsolute 1-based chunk number, continuing correctly across a resume.
STREAMING_FIRST_RECORDbothAbsolute number of the first record in this message.
STREAMING_LAST_RECORDbothAbsolute number of the last record in this message.
STREAMING_CHUNK_SIZECHUNKRecords actually in this message — smaller than ChunkSize for the final chunk.

Logging progress without a script mediator

These are enough to log a line every 10,000 rows with a plain filter. The XPath is true only on the message that crosses a 10,000 boundary:

<filter xpath="floor(number(get-property('STREAMING_LAST_RECORD')) div 10000)
             &gt; floor((number(get-property('STREAMING_FIRST_RECORD')) - 1) div 10000)">
    <then>
        <log level="custom">
            <property name="PROGRESS" value="rows streamed"/>
            <property name="milestone"
                      expression="substring-before(concat(floor(number(get-property('STREAMING_LAST_RECORD'))
                                  div 10000) * 10000, '.0'), '.')"/>
            <property name="chunk" expression="get-property('STREAMING_CHUNK_NUMBER')"/>
            <property name="rowRange"
                      expression="concat(get-property('STREAMING_FIRST_RECORD'), '-',
                                  get-property('STREAMING_LAST_RECORD'))"/>
        </log>
    </then>
</filter>
The substring-before trick

XPath 1.0 arithmetic yields a double, so floor(…) * 10000 prints as 10000.0. Concatenating '.0' and taking substring-before(…, '.') gives a clean integer in both cases.

17 · Four configurations

Each one is complete: the inbound, the sequence, and what comes out.

1 · CSV in chunks to a property, JSON reply file

orders.csv → CHUNK of 2000 → property streamOut → sequence builds a rollup → order-batches.jsonl

The workhorse shape for large files. Nothing of the file is in the message body, so the payload stays small and the sequence reads the chunk from a property.

inbound-endpoints/ordersInbound.xml

<?xml version="1.0" encoding="UTF-8"?>
<inboundEndpoint xmlns="http://ws.apache.org/ns/synapse"
                 name="ordersInbound"
                 class="org.wso2.carbon.inbound.streaming.VFSConsumer"
                 sequence="orderChunkSeq" onError="orderFaultSeq" suspend="false">
    <parameters xmlns="http://ws.apache.org/ns/synapse">
        <parameter name="scheduleType">Polling</parameter>
        <parameter name="interval">5000</parameter>
        <parameter name="sequential">true</parameter>
        <parameter name="coordination">true</parameter>

        <parameter name="transport.vfs.FileURI">/data/in</parameter>
        <parameter name="transport.vfs.FileNamePattern">.*\.csv</parameter>
        <parameter name="transport.vfs.FileProcessCount">1</parameter>
        <parameter name="transport.vfs.Locking">enable</parameter>
        <parameter name="transport.vfs.ActionAfterProcess">MOVE</parameter>
        <parameter name="transport.vfs.MoveAfterProcess">/data/out</parameter>
        <parameter name="transport.vfs.ActionAfterFailure">MOVE</parameter>
        <parameter name="transport.vfs.MoveAfterFailure">/data/fault</parameter>

        <!-- 2000 rows per message, as JSON objects keyed by the header -->
        <parameter name="transport.vfs.Streaming">true</parameter>
        <parameter name="transport.vfs.StreamingMode">CHUNK</parameter>
        <parameter name="transport.vfs.StreamingInputFormat">csv</parameter>
        <parameter name="transport.vfs.StreamingChunkSize">2000</parameter>
        <parameter name="transport.vfs.StreamingBufferSize">65536</parameter>
        <parameter name="transport.vfs.StreamingCsvHasHeader">true</parameter>
        <parameter name="transport.vfs.StreamingAddHeadersToEachResult">true</parameter>
        <parameter name="transport.vfs.StreamingOutputProperty">streamOut</parameter>

        <!-- numbers arrive as JSON numbers so the sequence can do arithmetic -->
        <parameter name="transport.vfs.StreamingCsvDataTypes">[{"Column Name Or Index":"order_id","Is Column Name":"Yes","Data Type":"Integer"},{"Column Name Or Index":"unit_price","Is Column Name":"Yes","Data Type":"Number"},{"Column Name Or Index":"quantity","Is Column Name":"Yes","Data Type":"Integer"}]</parameter>

        <parameter name="transport.vfs.ReplyFileURI">/data/replies</parameter>
        <parameter name="transport.vfs.ReplyFileName">order-batches.jsonl</parameter>
    </parameters>
</inboundEndpoint>

sequences/orderChunkSeq.xml

<?xml version="1.0" encoding="UTF-8"?>
<sequence name="orderChunkSeq" xmlns="http://ws.apache.org/ns/synapse">
    <script language="js"><![CDATA[
        var rows  = JSON.parse(mc.getProperty('streamOut'));
        var total = 0, flagged = [];
        for (var i = 0; i < rows.length; i++) {
            var line = rows[i].unit_price * rows[i].quantity;
            total += line;
            if (line > 10000) { flagged.push(rows[i].order_id); }
        }
        mc.setPayloadJSON({
            chunk:   mc.getProperty('STREAMING_CHUNK_NUMBER'),
            rows:    rows.length,
            revenue: Math.round(total * 100) / 100,
            review:  flagged
        });
    ]]></script>
</sequence>

Required for the body path with CSV

A raw CSV body needs a plain-text message builder, or MI tries to parse it as XML and every record fails with Unexpected character 's' (code 115) in prolog. Add this to <MI_HOME>/conf/deployment.toml and restart:

18 · Gotchas

  • Both streaming switches are needed. transport.vfs.Streaming defaults to false; StreamingMode alone does nothing.
  • Jars go in lib/, not dropins/. Copy the provided mi-inbound-streaming-1.0.0.jar and commons-csv-1.14.1.jar into <MI_HOME>/lib/, delete any stale dropins/mi_inbound_streaming_*.jar so MI regenerates the OSGi bundle, then restart. MI 4.1.0 does not ship commons-csv.
  • A raw CSV body needs PlainTextBuilder registered for text/csv in deployment.toml. Not needed when the output goes to a property.
  • A multi-line <format> breaks JSON Lines. Keep payloadFactory formats on one line when writing to a .jsonl reply file.
  • Do not symlink the registry to share it between nodes. Point GovRegRoot at the shared path instead.
  • Stopping MI: the process matches micro.integrator.bootstrap.Bootstrap, not wso2carbon. A forgotten node that still polls the same folder will compete for files and clear checkpoints out from under the node you are watching.
  • A re-copied file still resumes. Identity is content, not timestamp, so moving a file out and copying it back does not invalidate its checkpoint.
